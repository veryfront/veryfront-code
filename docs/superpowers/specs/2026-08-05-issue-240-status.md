## Objective

Replace runtime esm.sh delivery with a pinned, first-party, content-addressed dependency pipeline.

The issue bundles two distinct risks under one headline, and separating them is the single most useful thing to hold in mind when reading the rest of this document:

**Version drift.** Every package except `react` and `veryfront` is emitted unversioned and floats to whatever the registry published most recently. One floated major already produced a mass SSR 500 (`react-resizable-panels`, `PanelGroup` renamed). It also makes consecutive renders of an unchanged draft nondeterministic, so a library can change mid-session under a user or an agent iterating on a preview.

**A trusted third party in the request path.** esm.sh builds and serves every dependency at request time, sits in the CSP `script-src` allowlist, and is fetched inside cold SSR requests. An esm.sh outage is a total outage across all hosted projects simultaneously. An esm.sh compromise reaches every hosted project.

Pinning a version does not pin the bytes. Phase 0 closes the first risk and leaves the second untouched. Only content addressing (Phase 1) closes the second.

Secondary objectives unlocked by owning the pipeline: private registry support (structurally impossible today), air-gapped and on-premise deployment, and ingest-time supply-chain policy (age quarantine, deny-list, scanning).

## Phase 1: first-party immutable proxy

Goal: the renderer emits content-addressed URLs; on a cache miss the service fetches from esm.sh once, freezes the response into the store, and serves it immutably forever. esm.sh leaves the runtime availability path and the CSP.

This is where the availability and supply-chain risks actually close.

- [x] **Release 1**: durable artifact registry persistence in the API (`veryfront-api#4229`)
- [x] **Release 2**: runtime-only lookup, ensure, asset upload, and fenced result publication contracts (`veryfront-api#4231`). Deliberately read-only; `ensureDependencyArtifacts` cannot start asynchronous work. Staging-verified.
- [x] **Release 3**: deployable but inert dependency artifact builder (`veryfront-code#3208`, shipped in 0.1.1185). Strict lease-bound task input, content-addressed upload with local hash verification, full import-closure rewriting, and policy, origin, size, depth, and time enforcement.
- [ ] **Release 4A**: queue orchestration in the API. Blocked on nothing; Release 3 is deployed and verified.
- [ ] Renderer consumption. `src/release-assets/dependency-artifact-mode.ts` implements a complete four-mode rollout controller (`off`, `shadow`, `prefer`, `require`) and currently has **zero consumers**.
- [ ] Global `pkg@version` to artifact registry consulted live by `buildImportMap` for draft renders, with release manifests freezing a snapshot
- [ ] Origin-scoped registry keys, so private-scope mappings are namespaced per tenant. Designed now it is a column; discovered later it is a cross-tenant cache-poisoning bug.
- [ ] Drop esm.sh from the CSP `script-src` allowlist (`src/rendering/rsc/production-optimizer.ts:119`)

**Risk worth tracking:** three seams are inert and accumulating. Each additional inert release moves more risk into the single future moment when they are all wired together.

## Phase 2: own the transform

Goal: replace the esm.sh upstream with a first-party builder. npm tarball from the configured registry, integrity-checked, entry resolved via the `exports` map, bundled with esbuild, `react` and `react-dom` external, `target: es2022`.

- [ ] Tarball fetch and integrity verification
- [ ] Entry resolution via the `exports` map, **with separate conditions per target**: `deno`/`node` for the SSR artifact, `browser` for the client artifact
- [ ] esbuild pipeline into the same content-addressed store
- [ ] Transitive resolution against the project lockfile into import-map entries
- [ ] Per-scope registry mapping and credentials, following the `.npmrc` convention
- [ ] Pre-warm the 18 hardcoded install registries plus the top packages by real usage

The per-condition entry resolution is not a detail. `veryfront-code#3358` reproduced a hard failure where esm.sh selects the `browser` condition for `hast-util-from-html-isomorphic`, whose browser entry runs `new DOMParser()` at module scope, crashing Deno SSR outright. That is condition selection rather than version selection, so **Phase 0 does not fix it and neither does Phase 1**. Only owning the transform does.

## Follow-ups

- [ ] **SSR and browser artifact unification.** SSR pulls the same artifact the browser gets, from the store into `/tmp`, instead of separately downloading and rewriting esm.sh output per pod. Structurally shrinks the dual-React-identity bug class and stops cold SSR doing internet fetches inside requests.
- [ ] **Ingest-time policy hooks.** Extend the existing `minimumDependencyAge: P2D` guard to user dependencies; add quarantine windows, scanning, and a deny-list.
- [ ] **First-party extension client bundles into the same store.** Unblocks the class of client-side extensions the framework already has seams for (`MarkdownRendererProvider`, `CodeBlockRendererProvider`, both currently without any first-party provider).
- [ ] **Delete or reroute `rewriteBareImports` and `ModuleResolver`.** Both are public API surface with no internal caller, each carrying a divergent copy of specifier-to-URL logic. Safe today, but exactly where a future caller would silently reintroduce floating dependencies.
- [ ] **Private registry support.** Arrives with Phase 2. Reduces to configuration once resolution and transformation are owned.

## Notes for whoever picks this up

- **`url-builder.ts` is bundled into the RSC client graph.** Any edit to it makes `rsc-bundles.generated.ts` stale even when the changed code tree-shakes out. Run `deno task generate` in the same commit.
- **The local `.env` breaks env-sensitive tests.** Move it aside before running the full suite or pushing, since the pre-push hook runs the full suite.
- **`serveModule` flakes under `--parallel`** on `origin/main`, roughly 1 run in 3, with different steps each time. Not caused by this work.
- **Staging's renderer workload is the deployment named `veryfront-server`**, not `veryfront-renderer`. Ramp runbooks written against the latter will silently match nothing.
- **Production has no chart-only apply path.** Every ramp step needs an artifact promotion to take effect.
